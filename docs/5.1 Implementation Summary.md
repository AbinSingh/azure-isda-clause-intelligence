# ISDA 2002 Master Agreement Clause Intelligence

Project Summary: From Azure Document Intelligence to Clause Matching

So far, we have built the first part of a document-processing pipeline for ISDA 2002 Master Agreement PDFs.

The main achievement is that we have moved from extracting text from a PDF to organizing that text into a 
structured representation of legal clauses. This structure will eventually support clause-level search, 
retrieval-augmented generation (RAG), and answering questions about the contents of individual agreements.

I'll summarize the big picture first, then explain each component, how the pieces connect, what we have validated, 
and what comes next.

# 1. The Big Picture
What are we trying to build?

The goal is to build a system that can analyze ISDA 2002 Master Agreement documents and answer questions such as:

    - What does Section 2(a)(iii) say in this agreement?
    - What conditions must be satisfied before a party is required to make a payment?
    - What does the agreement say about netting of payments?
    - What obligations apply when a party must deduct or withhold tax?
    - Does this particular agreement contain a clause that differs from the standard structure?
    - Which section of the agreement supports the answer?

To answer these questions reliably, we need more than plain text extracted from a PDF.

We need to preserve the document's structure, identify clauses and subclauses, maintain their relationships, 
and retain the information needed to trace answers back to the original document.

# 2. Why Do We Need These Components?

Each component solves a different problem.

| Component                      | Main purpose                             | Problem it solves                                           |
| ------------------------------ | ---------------------------------------- | ----------------------------------------------------------- |
| Azure AI Document Intelligence | Extract document content and layout      | PDFs are not naturally structured data                      |
| Raw extraction preservation    | Retain the original extraction output    | Prevents useful information from being lost                 |
| Document parser                | Normalize the extraction result          | Gives downstream code a consistent data structure           |
| Clause registry                | Define the expected clause hierarchy     | Provides a reference structure for recognizing clauses      |
| Clause matcher                 | Identify clauses and their relationships | Converts extracted paragraphs into a legal clause hierarchy |
| Future chunker                 | Prepare searchable text units            | Makes clauses and relevant context suitable for retrieval   |
| Future index                   | Store searchable representations         | Enables efficient lookup                                    |
| Future retrieval system        | Find relevant clauses for a question     | Grounds answers in the actual agreement                     |

An important design principle is that document extraction, clause identification, and information retrieval are separate responsibilities.

Keeping them separate makes the system easier to test, debug, and improve.

# 3. Step 1 — Azure AI Document Intelligence #
##############################################

Purpose

The first challenge is converting a PDF into machine-readable content while preserving useful document layout information.

For this project, we are using Azure AI Document Intelligence with the prebuilt-layout model.

Conceptually:

        Input:
        ISDA_Master_Agreement.pdf
    
                 |
                 v
    
    Azure AI Document Intelligence
            prebuilt-layout
    
                 |
                 v
    
        Output:
            Extracted text
            Paragraphs
            Paragraph roles
            Page information
            Bounding regions
            Tables
            Sections
            Other layout information

The layout model is useful because the input is a legal document where paragraph boundaries, headings, numbering, and page references matter.

A simple PDF text extraction library might extract the words but give us less useful information about the structure in which those words appear.

# What we have established

Our pipeline uses Azure AI Document Intelligence to analyze the PDF and return an extraction result.

The extracted content includes information such as:

    Document text.
    Paragraphs and their text.
    Paragraph roles, such as sectionHeading.
    Page numbers.
    Bounding regions.
    Paragraph spans.
    Tables and sections, where present.
    Other document-layout information returned by the service.

For example, the service can extract a heading like:

# 1. Interpretation

and a paragraph like:

(a) Definitions. The terms defined in this Section 1...

It can also identify the following heading:

# 2. Obligations

These results provide the raw material for our clause-matching logic.

######################################
# 4. Step 2 — Document Normalization #
######################################

Purpose

Azure's output is detailed and service-specific. We do not want every downstream component to depend directly on the complete Azure response format.

Instead, we introduced a document parser that converts the extraction result into a consistent internal representation.

The relevant file is:

app/services/document_parser.py

The parser acts as a boundary between Azure and the rest of the application.

Conceptually:

What the parser currently captures

# A. Document metadata

The normalized document includes metadata such as:

    Azure API version.
    Model ID.
    String index type.
    Content format.
    Document ID, where supplied.
    PDF SHA-256 hash, where supplied.
    Source filename.

The source filename and hash are particularly useful when processing multiple agreements.

For example, two documents might both contain Section 2(a)(iii), but the actual wording may differ. We need to know which document a clause came from.

# B. Document content

The parser retains the overall extracted document content.

This is useful for inspection, debugging, and future processing.

# C. Paragraphs

Each normalized paragraph contains fields such as:

    {
        "paragraph_index": 12,
        "text": "...",
        "role": None,
        "spans": [],
        "page_numbers": [1],
        "bounding_regions": []
    }

This is an illustrative representation of the fields, not a complete Azure response.

The key attributes are:

| Field              | Purpose                                                 |
| ------------------ | ------------------------------------------------------- |
| `paragraph_index`  | Identifies the paragraph within the normalized sequence |
| `text`             | Contains the extracted paragraph text                   |
| `role`             | Preserves the detected paragraph role, when available   |
| `spans`            | Preserves source text-position information              |
| `page_numbers`     | Records the page or pages associated with the paragraph |
| `bounding_regions` | Preserves spatial information from the PDF              |

The paragraph index is particularly important.

The matcher processes paragraphs in document order, so the normalized paragraph sequence must remain stable.

# D. Other layout elements

The parser also preserves pages, tables, sections, and styles.

We may not need every field for clause matching, but retaining them provides flexibility for later enhancements.

# Why normalization matters

Without normalization, the matcher would need to know about Azure's internal response structures.

With normalization, its input is simply a list of paragraphs with consistent fields.

That means we can potentially replace or supplement the extraction provider later without rewriting the clause-matching logic.

Design decision: The document parser should normalize the extraction result, not decide which legal clause a paragraph belongs to.

###################################
# 5. Step 3 — The Clause Registry #
###################################

Purpose

The next problem is identifying legal clauses.

A PDF contains text, but our application needs to recognize a hierarchy such as:

1. Interpretation
    1(a) Definitions
    1(b) Inconsistency
    1(c) Single Agreement

2. Obligations
    2(a) General Conditions
        2(a)(i)
        2(a)(ii)
        2(a)(iii)
    2(b) Change of Account
    2(c) Netting of Payments
    2(d) Deduction or Withholding for Tax
        2(d)(i) Gross-Up

The clause registry provides a reference structure that describes the clauses we expect to encounter.

The file is: app/schemas/isda_clause_registry.json

The registry is a JSON representation of clause identities, numbering, titles, and parent-child relationships.

# Why have a registry?

Suppose the parser encounters:

(d) Deduction or Withholding for Tax.

    The registry can tell us that this is the subsection:

2(d) — Deduction or Withholding for Tax

Similarly, it can tell us that:

(i) Gross-Up.

    under Section 2(d) corresponds to:

2(d)(i) — Gross-Up

This helps distinguish a clause heading from the body text that follows it.

It also gives the application a consistent way to refer to clauses across different documents.

For example, 2(d)(i) can be used as a stable logical clause identifier within a document, even if the exact wording of the clause varies.

# The registry is a reference, not the document itself

This distinction is critical.

The registry defines the expected clause structure. It should not replace the actual text extracted from an agreement.

# Design decision: The registry provides expected clause structure and identities. The extracted agreement remains the source of truth for actual wording.


# 6. Step 4 — The Clause Data Model
Purpose

Once we identify a clause, we need a consistent Python object to represent it.

The model is defined in: app/models/clause.py

We created a Clause dataclass to hold the main information about a clause.

Its fields include:

| Field              | Purpose                                                  |
| ------------------ | -------------------------------------------------------- |
| `clause_id`        | Internal identifier for the clause                       |
| `clause_number`    | Human-readable legal numbering, such as `2(a)(iii)`      |
| `clause_title`     | The clause heading, when known                           |
| `parent_clause_id` | Identifier of the parent clause                          |
| `level`            | Depth within the clause hierarchy                        |
| `text`             | Text assigned to this clause                             |
| `document_id`      | Identifier of the source document                        |
| `source_filename`  | Source PDF filename                                      |
| `page_start`       | First page associated with the clause                    |
| `page_end`         | Last page associated with the clause                     |
| `child_clause_ids` | Identifiers of direct child clauses                      |
| `metadata`         | Additional information, such as source paragraph indices |

# Why we need a data model

We could represent every clause as an ordinary dictionary, but a dataclass gives us a clearer contract for the information that a clause should contain.

It also makes the next stages easier to design.

# 7. Step 5 — The Clause Matcher

Purpose

The clause matcher is the component that brings the earlier work together.

Its file is:

app/services/clause_matcher.py

It takes the normalized paragraphs and the clause registry, then attempts to organize the paragraphs into a 
hierarchical collection of Clause objects.

The transformation is:

Normalized paragraphs
        +
Clause registry
        |
        v
    Clause Matcher
        |
        v
List of Clause objects
        |
        ├── Clause identifiers
        ├── Clause numbers
        ├── Clause titles
        ├── Parent-child relationships
        ├── Clause text
        ├── Page ranges
        └── Source paragraph indices
