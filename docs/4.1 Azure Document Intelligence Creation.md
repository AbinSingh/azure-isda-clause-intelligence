# Step 5: Implement the Document Intelligence service

This is the central part of the implementation.

The service will:

    1. Accept a PDF file path.
    2. Calculate a SHA-256 hash of the file contents.
    3. Search app/data/ for an existing result with that hash.
    4. Return the cached result if found.
    5. Otherwise, submit the PDF to Azure using prebuilt-layout.
    6. Wait for the analysis to complete.
    7. Convert the result into JSON.
    8. Save the JSON using a UUID filename.
    9. Return the saved result.

I recommend storing the SHA-256 hash in the JSON metadata. This avoids having to maintain a separate cache-index file 
for a simple application.

# Important implementation detail

This implementation uses the SDK's AzureJSONEncoder to serialize the result object. The code converts the serialized JSON back into a Python dictionary so the service consistently returns a dictionary regardless of whether the result came from Azure or the cache.

The cache metadata is stored alongside the analysis:

        {
      "_cache_metadata": {
        "id": "b8c63b70-5f7e-4b2f-b8d1-ef01f3b902d1",
        "pdf_sha256": "example-sha256-hash",
        "source_filename": "invoice.pdf",
        "model_id": "prebuilt-layout"
      },
      "analyze_result": {
        "content": "Extracted document text...",
        "pages": [],
        "tables": []
      }
    }

This is a simplified illustration. The real analyze_result contains the actual information returned by Azure.

The metadata allows the application to determine which PDF produced the output without changing the Azure analysis result itself.

One caveat: This straightforward cache searches existing JSON files one by one. It is suitable for a small cache, but 
it will become inefficient if you accumulate thousands of documents. A SQLite index or database-backed cache would 
be a better choice at that scale.

# 7. A few recommendations before using this in production

Your proposed design is a good starting point. I would consider these additional points as the application grows.

| Concern               | Recommendation                                                                                           |
| --------------------- | -------------------------------------------------------------------------------------------------------- |
| Duplicate Azure calls | Add a cache index or locking if multiple requests may process the same PDF concurrently.                 |
| Large PDFs            | Consider file-size validation and appropriate request timeouts.                                          |
| Sensitive documents   | Restrict access to `app/data/` and establish a retention policy.                                         |
| Corrupted cache files | Log the error and treat the file as a cache miss, as the implementation does.                            |
| Model changes         | Include the model ID and API version in the cache identity.                                              |
| Large cache directory | Replace the JSON-file scan with SQLite or another indexed store.                                         |
| Azure credentials     | Use environment variables for local development and consider managed identity for deployed applications. |
| SDK upgrades          | Pin and test dependency versions before deploying.                                                       |

Also, app/data/ is fine for local development, but if this application runs in containers or on multiple servers, local 
files may not be shared or persistent. In that case, consider Azure Blob Storage or a database.

My final recommendation

For your current folder structure, use:

    - app/config.py for environment loading.
    - app/services/document_intelligence.py for the Azure integration and caching.
    - app/data/<uuid>.json for saved results.
    - SHA-256 to recognize identical PDF contents.
    - app/main.py as the application entry point.

This keeps the Azure-specific implementation separate from the rest of your application and gives you a clean foundation
for adding API endpoints or other document-processing workflows later.
