
The key idea is that our application will **transform extracted ISDA agreement text** into a **structured, searchable 
representation** of contractual provisions. Each service is responsible for a specific transformation, and the output of 
one service becomes the input to the next.

################################################
# 1. The big picture: ISDA Clause Intelligence #
################################################

Our objective is to build a retrieval system that can answer questions about signed ISDA Master Agreements by retrieving
the relevant contractual language.

For example, a user might ask:

    - What are the conditions for netting payments?
    - Does this agreement allow Multiple Transaction Payment Netting?
    - What obligations apply when a party must withhold tax?
    - What does Section 2(a)(iii) say about conditions precedent?
    - Show me the complete Netting of Payments provision.

To answer these questions reliably, the system must do more than extract text and create embeddings. 
It must understand the document's structure sufficiently to retrieve the correct contractual provisions.

# 2. What exactly is the services layer? #
##########################################

app/
└── services/
    ├── text_normalization.py
    ├── marker_detection.py
    └── structural_parser.py

Think of these as three stages in a processing pipeline.

| Service                 | Primary responsibility                 | Input               | Output                                          |
| ----------------------- | -------------------------------------- | ------------------- | ----------------------------------------------- |
| `text_normalization.py` | Prepare extracted text for analysis    | Raw extracted text  | Normalized working text                         |
| `marker_detection.py`   | Identify potential structural markers  | A line or paragraph | Candidate marker and its properties             |
| `structural_parser.py`  | Build the document's initial hierarchy | Extracted text      | Sections, clauses, associated text and warnings |

# Service 1: text_normalization.py
----------------------------------

- Purpose

    Convert extracted PDF text into a more consistent representation that our parser can process.

Azure AI Document Intelligence may return text containing formatting artifacts because PDF files are designed for visual presentation, not necessarily for clean text extraction.

Your sample illustrates this. The extracted content contains:

| **2.** | **Obligations** |
| ------ | --------------- |

The actual contractual heading is:

    2. Obligations

Our parser needs to recognize that heading even though the extraction output represents it as a Markdown table.

What does it currently do?

    - A. Normalizes whitespace
    - B. Removes Markdown emphasis delimiters (******)
    - C. Converts simple Markdown heading tables
    - D. Normalizes excessive blank lines

Why do we need this service?

Without normalization, we would need to write structural detection rules for every possible formatting variation.

For example, the same heading might appear as:

2. Obligations

or:

**2.** **Obligations**

or as a row in a Markdown table.

Normalization reduces these differences before the structural parser runs.

# An important design decision

We should preserve two representations:

Original extracted text: The source-derived text retained for evidence and auditability.
Normalized working text: The representation used for structural analysis.

# 4. Service 2: marker_detection.py
-----------------------------------

Purpose

Identify possible structural markers without deciding the complete document hierarchy.

Your ISDA text uses several numbering conventions.

For example:

    2. Obligations

    (a) General Conditions.
    
    (i) Each party will make each payment...
    
    (1) promptly notify the other party;
    
    (A) the failure by Y to comply...

These markers provide clues about the structure of the agreement.

Our marker_detection.py service identifies those clues.

# How does it work?

The current implementation uses regular expressions to recognize candidate patterns.

For example:

    SECTION_RE = re.compile(
        r"^\s*(\d{1,2})\.\s+(.+?)\s*$"
    )

This pattern can identify a section heading such as:

    2. Obligations

It extracts:

    Identifier: 2
    Remainder: Obligations

The service also recognizes parenthesized markers, such as:

    (a) General Conditions.
    (i) Each party will make each payment...
    (1) promptly notify the other party;
    (A) the failure by Y to comply...

It returns a candidate marker and information about the text following it.

Conceptually, the output looks like this:

    {
  "marker_type": "section",
  "identifier": "2",
  "remainder": "Obligations",
  "raw_line": "2. Obligations"
    }

For a parenthesized marker:

    {
  "marker_type": "lower_alpha_or_roman",
  "identifier": "ii",
  "remainder": "Payments under this Agreement...",
  "raw_line": "(ii) Payments under this Agreement..."
    }

# The responsibility boundary

marker_detection.py answers: What structural marker might this text contain?

It does not yet answer: What is the full structural path of this text in the agreement?

That second question belongs to structural_parser.py.

This separation makes the code easier to maintain and test.


# 5. Service 3: structural_parser.py
------------------------------------

Purpose

Determine which section and clause each piece of text belongs to, and assemble an initial representation of the 
document hierarchy.

This is the most important of our three current services.

The marker detector might recognize (c), but the structural parser must understand that it starts a new clause within 
Section 2.

For example:

    2. Obligations
    
    (a) General Conditions.
    
    (i) Each party will make each payment...
    
    (ii) Payments under this Agreement...
    
    (b) Change of Account.
    
    (c) Netting of Payments.

The structural parser should produce a representation resembling:

    Section 2: Obligations
    │
    ├── Clause (a): General Conditions
    │   ├── Subparagraph (i)
    │   └── Subparagraph (ii)
    │
    ├── Clause (b): Change of Account
    │
    └── Clause (c): Netting of Payments


How does the current parser work?

At a high level, it:

    Normalizes the supplied text.
    Splits the text into paragraphs using blank lines.
    Looks for section headings.
    Creates a section node when it detects a heading.
    Looks for top-level lettered clauses inside the active section.
    Creates clause nodes and associates subsequent text with them.
    Collects text that could not be assigned to a section.
    Emits warnings for some unresolved structures.

What does the output look like?

    {
  "node_id": "section-2-1",
  "node_type": "section",
  "identifier": "2",
  "title": "Obligations",
  "text": "2. Obligations",
  "children": []
    }

A clause node might look like this:

    {
  "node_id": "section-2-1-clause-c",
  "node_type": "clause",
  "identifier": "(c)",
  "title": "Netting of Payments",
  "parent_node_id": "section-2-1",
  "text": "(c) Netting of Payments. ...",
  "children": []
    }

The children field will eventually represent nested provisions, while the parent identifier will let us trace each 
provision back to its containing section or clause.

# Why is this important for RAG?

Suppose a user asks:

What does the agreement say about Multiple Transaction Payment Netting?

If we simply split the agreement into fixed-size chunks, the relevant paragraph might be separated from its clause heading.

Our parser can preserve the fact that the paragraph belongs to Section 2(c), Netting of Payments.

Later, our chunking service can use that information to create a searchable record with meaningful metadata.

That allows retrieval results to include both the relevant text and its contractual location.

# 6. How the three services work together #
###########################################

Let's trace a simplified example from your agreement.

Input:

    | **2.** | **Obligations** |
    | ------ | --------------- |
    
    (c) ***Netting of Payments.*** If on any date amounts would otherwise be payable:—
    
    (i) in the same currency; and
    
    (ii) in respect of the same Transaction,
    
    by each party to the other, then...

# Stage 1: Text normalization

The Markdown heading table becomes: 2. Obligations

# Stage 2: Marker detection

The detector recognizes candidate markers:

    2.  -> possible section heading
    (c) -> possible lettered clause
    (i) -> possible nested marker
    (ii) -> possible nested marker

# Stage 3: Structural parsing

    The parser identifies the section and top-level clause:

    Section 2: Obligations
    └── Clause (c): Netting of Payments

# Future stage: Chunking

Once the hierarchy is reliable, the chunking service could produce:

    Parent:
    Section 2(c) — Netting of Payments
    
    Child 1:
    Standard payment-netting conditions and mechanics
    
    Child 2:
    Multiple Transaction Payment Netting election and application

These are retrieval-oriented units derived from the structural representation, rather than arbitrary text fragments.

# 9. One architectural principle I want us to follow

For this project, I recommend a clear distinction between three representations of the same agreement:

| Representation      | What it contains                                            | Why it exists                             |
| ------------------- | ----------------------------------------------------------- | ----------------------------------------- |
| Extracted document  | Text and layout information obtained from the PDF           | Preserve the extraction result            |
| Structural document | Sections, clauses, nested provisions, and source references | Understand the contractual hierarchy      |
| Retrieval chunks    | Parent and child text units with search metadata            | Retrieve the right provisions efficiently |


These representations should not be conflated.

For example, a structural node may correspond to an entire clause, while a retrieval chunk may represent only one meaningful paragraph within that clause.

Likewise, the extracted text might contain line breaks that are useful for provenance but unnecessary for determining the clause hierarchy.

Keeping these representations separate makes it easier to improve our parsing and chunking strategies without repeatedly changing the rest of the application.

# My recommendation for the next step

Before we implement more code, I would keep the responsibilities of the existing modules fixed:

    text_normalization.py: Make extracted text consistent without changing contractual meaning.
    marker_detection.py: Identify candidate structural markers.
    structural_parser.py: Determine the hierarchy and assign text to its correct structural parent.

Then we should extend structural_parser.py to handle the nested numbering in your supplied agreement, particularly 
Section 2(d), where letters, Roman numerals, Arabic numerals, and uppercase letters appear at multiple levels.

Once the parser can correctly represent those relationships, we can build chunking.py on top of it.

The central design principle is simple: first understand the document's structure, then create retrieval chunks from 
that structure. That gives us a much stronger foundation for reliable ISDA Clause Intelligence than starting with 
embeddings or fixed-size text splitting.
